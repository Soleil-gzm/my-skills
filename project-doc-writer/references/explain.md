# 场景 ⑤：解释文档与架构

不写文档，而是**读**——跨文本、代码注释、图、测试综合出解释。用用户的语言回答（中文提问用中文答），技术标识符保留原文。

## 渐进式探索（不要一次全读）

1. **Overview**：README、docs/architecture.md
2. **定位**：确定与问题相关的子系统/模块
3. **细节**：读该模块的专门文档
4. **交叉验证**：对照代码和测试
5. **综合**：多来源拼成完整解释

## 文档类型速查

| 类型 | 常见位置/文件名特征 | 回答的问题 |
|------|--------------------|-----------|
| 架构规格 | `docs/architecture*`、`*_spec.md` | "X 怎么工作？" |
| 实现指南 | `*_implementation.md`、`*_guide.md` | "Y 怎么实现？" |
| API 参考 | `*_api.md`、接口定义、头注释 | "X 接收什么参数？" |
| 测试计划 | `*_test_plan.md`、测试文件、断言 | "X 被验证过吗？" |
| 调试/已知问题 | `*_debug.md`、`*_issues.md`、CHANGELOG | "X 为什么挂了？" |
| 设计缘由 | spec 里的 Rationale 小节、commit message | "为什么这样设计？" |

内容信号词：Rationale/Why → 设计决策；Must/Shall → 需求；Known Issue/Workaround → 调试；TODO/Status → 进度。

## 代码即文档

除了 md 文件，还要挖：
- 模块/类头注释（目的、输入输出、设计缘由）
- 接口定义（契约）
- 函数 docstring（算法、参数、返回）
- 行内注释（非显而易见的逻辑）
- 断言信息（预期行为）
- 测试描述（验证意图、边界场景）
- 命名约定（隐式文档）

## 回答模板

**"X 怎么工作？"**：一句话目的（来自 spec）→ 架构与关键组件 → 接口 → 运行机制（spec + 代码 + 注释）→ 一个具体例子（来自测试）→ 相关组件链接。

**"为什么这样设计？"**：决策原因 → 考虑过的替代方案 → 权衡（优势/劣势）→ 驱动约束 → 当前实现状态。

**"X 怎么和 Y 集成？"**：接口描述 → 信号/字段清单 → 数据流时序 → 所需配置 → 现有集成示例 → 常见问题。

**"X 有什么已知问题？"**：问题清单 → 症状 → 根因 → workaround → 状态（fixed/open/wontfix）→ 相关测试。

## 交叉验证

代码 = "实际是什么"的事实来源；spec = "当初想做成什么"；测试 = "验证过什么"；注释 = "为什么这样写"。

发现冲突时：指出矛盾 → 用 git history/时间戳判断哪个更新 → 检查 known_issues → 建议更新文档。

发现文档缺口要显式标注：实现了但无 spec、复杂算法无注释、有测试但无测试计划等。

## 质量信号

**好文档**：有设计缘由、图与代码一致、接口契约清晰、有例子、已知限制有记录。
**要提醒用户的缺口**：复杂逻辑无注释、spec 与代码不一致、模块无文档、特性无测试。

## 注意

- 自动生成的文件（有 "AUTO-GENERATED - DO NOT EDIT" 头）只当参考读，不建议直接改，指引用户去改源数据
- 多语言文档：保留技术术语原文，设计缘由翻译成用户语言
- 别解释用户没问的显而易见的内容
